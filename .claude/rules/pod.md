# The RunPod dev pod

A GPU pod on RunPod for the work that crawls this machine when several agents run at once: shot scripts, benchmarks, Blender builds. Optional; everything still runs locally. The pod is a Linux box with an RTX-class GPU, reached over SSH (VS Code Remote-SSH works), with the repo, Node, the browser and Blender on a network volume.

**Where it lives.** A pod named `rainy-place-*` (the prefix finds it), US-IL-1, on the network volume `rainy-place-dev-il1` (60 GB) mounted at `/workspace`. Billing is per hour while it runs (about $0.27 an A5000, $0.89 a 4090); stopped, only the volume costs (about $0.07 per GB a month). Volumes can't shrink and a pod can only mount a volume in its own datacenter. A stopped pod is tied to its host machine, and if that machine's GPU has been taken it can't restart ("not enough free GPUs"): `pod.mjs start` then makes a new pod on the same volume (graphics-capable cards, cheapest first: A5000, 3090, L4, RTX 4000 Ada, 4090; `POD_GPUS` overrides) and deletes the old one, which only held a wiped container disk. The old 250 GB volume was dropped when the Krea 2 checkpoint moved to Hugging Face.

**Agents use it through `run`, and `run` starts it.** Nothing sends work to the pod by itself: an agent runs a heavy command with `node scripts/pod.mjs run [--wait] [--no-sync] [--no-pull] [--full] [--out <dir>] -- <command...>`, which syncs this checkout, runs the command there from the repo root and pulls back what it wrote. The instruction is in CLAUDE.md, so only sessions that started after it was written follow it. If the pod is stopped, `run` starts it in the background (one start at a time, a lock in `~/.pod-sync/start.lock`; log `~/.pod-sync/start.log`) and exits 3: the agent runs locally this once. With `--wait` it starts the pod itself and blocks until it is booted (2-4 minutes, 11 in the one measured case where the host had to be replaced), so the caller needs a long timeout. The cost is bounded by the idle stop below. Turn autostart off with `POD_AUTOSTART=0` or by creating `~/.pod-sync/autostart-off`: `run` then exits 3 with "autostart is off" and agents run locally. `running` exits 0 only when the pod is up and its boot step has finished (`/tmp/pod-boot-done`, written by `podSetup.sh`). Claude Code itself stays on this machine; only the commands go to the pod (Claude Code on the pod over Remote-SSH works too, with its login folder moved to `/workspace`, but isn't set up).
- The sync sends only files changed since this checkout's last sync (a manifest in `~/.pod-sync/`) and deletes what was deleted here; tracked and untracked files git doesn't ignore, uncommitted work included, nothing committed or pushed. After a `package.json` change run `npm install` on the pod (`run -- npm install`).
- The pull-back takes files the command wrote under `debug-shots/` (and each `--out` folder), newer than the start of the run, leaving out source (`.mjs .js .ts .py .sh .html .css .md`) so a run never overwrites code here. A command that writes elsewhere needs `--out` (the cast builds: `--out assets/humans`).
- A checkout under `.claude/worktrees/<name>` gets its own folder on the pod, `/workspace/wt/<name>`, with the main checkout's `node_modules` linked in, so agents on different worktrees don't overwrite each other. Agents on the main checkout share one folder, which is fine: it is the same tree.
- The GPU queue (`CITYPOP_GPU`, `scripts/shotServer.mjs`) stays on there, so several agents' runs share the pod's GPU the way they share this one's, and a benchmark still waits for exclusive use.
- The other commands (`scripts/pod.mjs`; the RunPod key is read from `RUNPOD_API_KEY` or the Trame studio's `.env`, the SSH key is `~/.ssh/runpod_ed25519`): `start` starts the pod, waits for SSH, runs `podSetup.sh --boot` and writes `Host rainy-pod` into `~/.ssh/config` (the address changes at each start: run it before connecting from VS Code); `sync [--full]`, `ssh [cmd]`, `pull <remote> [dir]`, `status`, `running`, `stop`. A run's timestamps come from the network filesystem, which keeps whole seconds only: that is why the run's marker is backdated two seconds.

**A pod's container disk is wiped at every stop**; only `/workspace` survives. So the apt packages (the GL and Vulkan libraries, Chromium's system libraries, the Japanese and Liberation fonts and their fontconfig aliases for the Windows names the code asks for: Consolas, MS Gothic, Yu Gothic, Meiryo) are reinstalled at each boot by `podSetup.sh --boot` (about a minute). Blender's per-user folder is `/workspace/blender-user`, linked as `~/.config/blender/5.2`: its config, the MPFB extension and MPFB's 1.8 GB of MakeHuman asset packs were copied once from this machine's `%APPDATA%\Blender Foundation\Blender\5.2`. `BLENDER=/workspace/blender/blender` runs the cast scripts (`human_figures.py` rebuilds a figure in about 11 s there).

**The dashboard shows it.** `node scripts/pod.mjs status --json` prints the one line agent-notify's Resources tab reads (`state`, `fields`, which `actions` apply now): the cost so far, how long it's been up, and an `activity` list of the agent runs on it: each `run` leaves a file in `~/.pod-sync/runs/` while it works, holding the script it runs, the full command, when it started and the agent's session id (`CLAUDE_CODE_SESSION_ID`, which Claude Code gives its Bash tool), and the tab shows each row as the agent's project and what its session is about, what it's running and for how long. A run started from a terminal by hand has no session and shows as such. `pod.mjs autostart [on|off]` is the "let agents start it" switch. The tab's Start, Stop and autostart buttons run `pod.mjs start`, `stop` and `autostart`; the wiring is a `resources` entry in `~/.agent-notify.json` (see the kit's README), not code in the kit. The kit is a separate repository (`agent-concurrency-kit`).

**Playing on the pod** (`node scripts/pod.mjs play`; an experiment, still being judged by feel). It starts the pod if it's stopped, syncs this checkout, starts a desktop on the pod and holds an SSH tunnel to a page on `http://localhost:8450/`, which it opens. The desktop is Xvfb, openbox, the game's dev server on 5173 and Playwright's Chromium in kiosk mode on the NVIDIA GPU (ANGLE + Vulkan, the shot scripts' path). **The stream is H.264 from the GPU's video encoder** (`scripts/podStream.sh`, `scripts/stream/`): `ffmpeg` grabs the display (x11grab) and encodes it with `h264_nvenc` (ultra-low-latency preset, CBR 25 Mbit/s at 1080p, keyframe every half second, an access-unit delimiter per frame); `server.mjs` cuts the byte stream into frames and sends each over a WebSocket; `client.html` decodes them with WebCodecs (hardware decode in the browser) onto a canvas and sends mouse (pointer lock, relative moves merged at about 160 Hz) and keyboard back, which `input.py` injects into the display with XTest. The server listens on 127.0.0.1 only. The encoder runs only while a viewer is connected. The page shows a stats line (frames, Mbit/s, round trip, decode ms). Click to capture the mouse, Esc releases it (and sends the game an Esc, so its own pointer lock lets go), F for fullscreen. Verified: input (W took the car to 57 km/h, S braked, absolute and relative pointer moves landed on the exact pixel); not yet judged by a person: mouse-look under pointer lock and the feel. **No sound** (nothing carries the pod's audio). `play stop` stops it, `play --kasm` runs the older KasmVNC version (`podPlay.sh`, below).

**The pod's browser renders wrong without `--disable-gpu-compositing`** (found while chasing green squares in the stream, which were not the stream's): the same view rendered four ways showed the PC's Direct3D clean, the pod's Vulkan with big dark rectangles, garbled HUD text and green patches on the ground, and only Vulkan with GPU compositing off clean. The game's WebGL stays on the GPU; only the page's final assembly moves to the CPU. `launchBrowser.mjs` adds it on Linux, so the agents' shots from the pod were affected too (corrupted pictures before this). The OpenGL (EGL) backend renders clean in a headless browser but on a headed display (Xvfb) falls back to Mesa's software renderer (llvmpipe, under 1 fps): not usable there. A real NVIDIA X server (Xorg with `nvidia_drv.so`, which the container does have) cannot start: "Failed to acquire modesetting permission", because the container's device policy denies even root the DRM nodes (`/dev/dri/card*`), so there is no GPU-resident capture or presentation (no NVFBC, no Selkies-style zero-copy) on RunPod as it stands.

**Size against frame rate**, with the clean flag, the game's own frame rate read by `podFps.mjs`, a viewer attached, on an A5000 pod: 2160x904 (1.95 M pixels, the default, the shape of a 21:9 monitor) 60, 2560x1080 about 33, 3440x1440 about 21. That is a ceiling of roughly 100 million pixels a second through Chromium's software compositing and the X copies (Chromium into Xvfb, `x11grab` out of it), single-threaded and CPU-bound; the GPU (25-30% busy) and its encoder (about 15-20%) are not the limit. Native 3440x1440 at 60 would need three times that, so on this setup the stream is sharper than the first KasmVNC attempt but not native on an ultrawide, and it is upscaled in the browser (about 2.5 times fewer pixels). Earlier, higher numbers for the big sizes (41 and 24) came from the corrupted render and from about 1.5 cores burnt by leftover KasmVNC processes. **Lesson: never pipe a long-lived command into `tail` in a script that ends** (`vncserver ... | tail -6` left `perl vncserver` and `tail` at 100% and 55% CPU for two hours); and check `ps` for strays before measuring. Decode time measured in a headless test browser (100-150 ms at the large sizes) is software decoding and says nothing about a real browser. Past this limit would need a different class of host (a VM with a real display GPU, not a container).

**The first attempt, KasmVNC (`play --kasm`, `podPlay.sh`), was worse and is kept only as a fallback.** It compresses every frame on the CPU (JPEG/WebP of the changed rectangles), so the game's frame rate fell as the picture grew (60 at 1280x720, 50-55 at 1600x900, 37 at 1920x1080, 22 at 2560x1080 with quality 9), and changed regions show as boxes: a muzzle flash draws as a square. Also found there: its web client's "remote resizing" sizes the pod's desktop to the browser page in CSS pixels, which on a 3440x1440 monitor at 150% Windows scaling gave a 1608x614 desktop stretched 1.5x (the first launch was soft because of that, not the quality sliders, which changed nothing); the server config now fixes the size (`desktop.allow_resize: false`) and the client's own defaults (quality 6, a 960x540 cap on video mode) are overridden (`allow_client_to_override_kasm_server_settings: false`). Quality 9 and lossless settings cost frames and gave decode errors. Each launch deletes the browser profile and sets the window size (Chromium reuses the last window's size otherwise).

**UDP works on RunPod** (a pod created with a `/udp` port, e.g. `60000/udp`, gets an external port mapped to it: 300 of 300 datagrams echoed, median 29 ms from Ohio to US-IL-1), so WebRTC streaming is possible; the stream above uses a WebSocket through an SSH tunnel instead, which is simpler and, on this short clean path, fine. The external port is random, which suits a single-port WebRTC server and not Sunshine or Moonlight (fixed port offsets); the `70000/udp` "symmetric" placeholders hung a pod when requested through the API. **The game keeps rendering whether or not anyone watches**, which would keep the GPU busy and the pod's idle stop from ever firing, so each desktop stops itself after 10 minutes with no viewer connected or 30 minutes with no input (`server.mjs`, `STREAM_NO_VIEWER_MIN` and `STREAM_IDLE_MIN`; KasmVNC's `/tmp/play-watch.sh`, `/var/log/podPlay.log`). Playing doesn't count as agent work, so it won't show in the dashboard's activity list, and it shares the pod's GPU with the agents' shots.

**The browser is launched in one place**, `scripts/launchBrowser.mjs`, which every shot script and benchmark calls instead of `chromium.launch`: Edge with ANGLE on Direct3D 11 on Windows (unchanged), Playwright's Chromium with ANGLE on Vulkan on Linux (`--use-angle=d3d11` is swapped for the Vulkan flags, `--no-sandbox` added, a headed run with no display runs headless). `BROWSER_PATH`, `BROWSER_CHANNEL` and `BROWSER_ARGS` override it (Brave works through `BROWSER_PATH`). New scripts use it, never `chromium.launch`. `node scripts/gpuCheck.mjs` says which flag set reaches the real GPU; Chromium's default and ANGLE-GL fall back to SwiftShader on the pod, only Vulkan and EGL get the card. Frame times from the pod aren't comparable with this machine's GTX 1070 Ti: compare a change against a pod run, not against a local one. The district benchmark ran at about 64 fps on the A5000.

**It stops itself.** `scripts/podIdleStop.sh` (started by `podSetup.sh`) stops the pod through RunPod's API, with the pod's own id and key (in PID 1's environment), after 45 minutes with the GPU under 5 %, the container's own CPU use under half a core and no Blender, browser or ffmpeg running, and in any case 12 hours after the boot. An open editor window doesn't count as busy. `touch /workspace/.keep-awake` pauses it for a long job; `/workspace/podIdleStop.log` says why the last stop happened, and `/var/log/podIdleStop.log` on the pod has a status line every 15 minutes (what it saw, and why it counted the pod busy or idle). Tune with `IDLE_MIN`, `MAX_HOURS`, `CPU_BUSY_CORES`. **Never judge idleness by `/proc/loadavg`: inside a pod it is the whole host's load, other customers included** (5,000+ processes against the container's dozen), which is why the first version, which used it, left the pod running for 11 hours overnight; CPU is read from the container's cgroup instead.
